\begin{abstract}\noindent
Memory Slice (\texttt{.msl}) is a self-describing, block-based binary format for capturing the forensic state of a single operating system process. It records both the virtual address space (with per-page acquisition status) and transient OS-queryable metadata that exists only while the process is alive. This document specifies the binary layout: file header, block architecture, integrity chain, capture-time payloads, extension segments for post-acquisition enrichment, cross-referencing, capability bitmap, raw dump import mechanism, investigation mode with system-wide context capture, and full-container AEAD encryption with post-quantum key encapsulation support.
\end{abstract}

\vfill
{\small\color{muted}
This specification accompanies the research paper \emph{Memory Slice: A Process-Centric Dump Format for Differential Memory Analysis and Volatility 3 Plugin Synthesis}.}
\end{titlepage}

\section{Scope and Conventions}
%% ======================================================================
\subsection{Scope}
This document defines the binary wire format of Memory Slice (\texttt{.msl}) files. It does \emph{not} specify acquisition procedures or analysis algorithms.

\subsection{Normative Language}
The key words \MUST, \MUSTNOT, \REQUIRED, \SHALL, \SHALLNOT, \SHOULD, \SHOULDNOT, ``RECOMMENDED'', \MAY, and \OPTIONAL{} are per RFC~2119~\cite{rfc2119}.

\subsection{Encoding Conventions}\label{sec:encoding}
\begin{itemize}[leftmargin=1.5em, itemsep=3pt]
\item All multi-byte structural integers are \textbf{little-endian}. The file header's \field{Endianness} byte at offset~\hex{08} \MUST{} be \hex{01} in version~1.1. The field is retained for forward compatibility; future versions \MAY{} define \hex{02} (big-endian). Consumers encountering a value other than \hex{01} \MUST{} reject the file.
\item Strings are UTF-8, null-terminated, padded to \textbf{8-byte} boundaries with zero bytes. The pad function is defined as $\padeight(n) = \lceil n/8 \rceil \times 8$, where $n$ is the byte length of the UTF-8 encoded string \textbf{including} the mandatory terminating NUL (\hex{00}). All padding bytes \MUST{} be \hex{00}. Textual string fields \MUSTNOT{} contain \hex{00} bytes before the terminating NUL.
\item Where a string field is accompanied by an explicit length field (e.g., \field{PathLen}, \field{ExePathLen}), the \textbf{length field is authoritative}: it specifies the byte count including the terminating NUL. The on-disk storage occupies $\padeight(\text{Len})$ bytes. Consumers \MUST{} use the length field to determine string extent and \MUSTNOT{} scan beyond \field{Len} bytes. The NUL byte at position $\text{Len}-1$ serves as a consistency check.
\item Producers \MUST{} emit well-formed UTF-8 per RFC~3629~\cite{rfc3629}. Consumers encountering invalid UTF-8 sequences \SHOULD{} preserve the raw bytes and \MAY{} flag the field as malformed, but \MUSTNOT{} reject the entire block. This ensures that forensic evidence is never silently discarded due to encoding errors in captured metadata.
\item Variable-length fields (\field{PageStateMap}, \field{NativeBlob}) are padded to 8-byte boundaries.
\item UUIDs \MUST{} be version~4 (random) per RFC~9562~\cite{rfc9562}, stored as 16 raw bytes in RFC~9562 binary layout. See Section~\ref{sec:uuids}.
\item Integrity hashes use the algorithm selected by \field{HashAlgo} (Section~\ref{sec:hashchain}); all registered algorithms produce 32-byte output. The default is BLAKE3~\cite{blake3}.
\item Timestamps: unsigned 64-bit nanoseconds since Unix epoch (1970-01-01T00:00:00Z).
\item All \field{Reserved} fields \MUST{} be zero (producers) and \MUST{} be ignored (consumers).
\end{itemize}

\subsection{Byte Order Domains}\label{sec:byteorder}
Three byte-order regimes coexist within an MSL file. Implementers \MUST{} observe the boundaries precisely:
\begin{enumerate}[leftmargin=1.8em, itemsep=2pt]
\item \textbf{Structural integers.} All multi-byte integers in the file header, block headers, and payload fixed fields are little-endian (controlled by \field{Endianness}=\hex{01}).
\item \textbf{UUIDs.} All UUID fields are stored in RFC~9562 binary layout (big-endian mixed-endian per the RFC) and are \emph{never} subject to byte-swapping, regardless of the file's \field{Endianness} setting.
\item \textbf{Captured memory content.} Bytes within \field{PageData} are stored verbatim in the target architecture's native byte order; the format does not reorder them.
\end{enumerate}

\subsection{UUID Requirements}\label{sec:uuids}
All UUID fields (\field{DumpUUID}, \field{BlockUUID}, \field{ParentUUID}, payload UUIDs) \MUST{} be version~4 (random) per RFC~9562. The 4-bit version field (bits 48--51) \MUST{} be \texttt{0100}; the 2-bit variant (bits 64--65) \MUST{} be \texttt{10}. UUIDs are stored as 16-byte sequences in RFC~9562 binary layout and are never subject to byte-swapping.

\begin{notebox}[title={Implementation guidance: UUID generation}]
A thread-local fast PRNG such as \texttt{xoshiro256++} or \texttt{PCG64}, seeded once from OS entropy, provides sufficient uniqueness ($\sim\!2^{-61}$ collision probability per pair) while avoiding CSRNG overhead per block. Note that this is a \emph{performance optimization}, not a conformance requirement; implementations \MAY{} use a CSRNG if preferred.
\end{notebox}

\subsection{Terminology}
\begin{description}[style=nextline, leftmargin=2em, itemsep=4pt]
\item[Producer] Software that creates or appends blocks.
\item[Consumer] Software that reads an MSL file.
\item[Acquirer] A producer capturing live process state (types \hex{0000}--\hex{0FFF}).
\item[Importer] A producer converting a raw dump into MSL (Section~\ref{sec:import}).
\item[Enrichment tool] A producer that appends extension segments (Section~\ref{sec:extsegments}) to an existing file.
\item[Block] Fixed header + variable payload.
\item[Payload] Block-type-specific data after the header.
\item[Preamble] Block-level fields at the start of a payload that precede repeated entry structures (e.g., \field{EntryCount}).
\item[Capture segment] Block~0 through the End-of-Capture block: the evidence as written by the acquirer or importer (Section~\ref{sec:eoc}).
\item[Extension segment] One or more blocks appended after the capture segment and terminated by an End-of-Extension block (Section~\ref{sec:extsegments}).
\item[Investigation Mode] Acquisition for forensic investigations with system-wide context (Section~\ref{sec:investigation}).
\item[Analysis Mode] Default mode for research and tool development. No system-wide context required.
\end{description}

\section{Format Overview}\label{sec:overview}

Block~0's \field{PrevHash} = $H(\text{File Header})$, where $H$ is the hash selected by \field{HashAlgo} (\blake{} by default; Section~\ref{sec:hashchain}). Each subsequent block hashes its predecessor. The capture segment ends with the End-of-Capture block (Section~\ref{sec:eoc}) and \MAY{} be followed by extension segments (Section~\ref{sec:extsegments}). Consumers detect end-of-file when fewer than 80 bytes remain or the next 4 bytes do not match the block magic (\hex{4D534C43}). Every non-zero block count---in the file header or in the EoC block---\MUST{} equal the number of capture-segment blocks actually parsed (Section~\ref{sec:basehdr}, \emph{BlockCount semantics}).

\subsection{Acquisition Modes}\label{sec:modes}
The file header's \field{Flags} field (offset~\hex{0C}) determines the acquisition mode and whether encryption is active:

\begin{description}[style=nextline, leftmargin=2em, itemsep=4pt]
\item[\textbf{Analysis Mode} (\field{Investigation}=0)] The default. For research and developing new forensic approaches. Header is 64~bytes. No system-wide context required. Figure~\ref{fig:acq-sequence}.
\item[\textbf{Investigation Mode} (\field{Investigation}=1)] For forensic investigations. Block~2 \MUST{} be a System Context block (\hex{0050}). Section~\ref{sec:investigation}. Figure~\ref{fig:inv-combined}.
\end{description}

\noindent Either mode \MAY{} set the \field{Encrypted} flag (bit~2), activating full-container Authenticated Encryption with Associated Data (AEAD) as defined in Section~\ref{sec:encryption}. When set, \field{HeaderSize} is~128 and the entire block stream is encrypted. Table~\ref{tab:mode-summary} summarizes the combinations.

\subsection{Design Principles}
\begin{enumerate}[leftmargin=1.8em, itemsep=2pt]
\item \textbf{Integrity Verification.} Append-only policy with a hash chain (\blake{} by default).
\item \textbf{Epistemic Honesty.} Four-state pages: Captured vs.\ Failed vs.\ Unmapped vs.\ NotResident.
\item \textbf{Self-Describing.} Version, header size, OS, arch, PID, capabilities.
\item \textbf{Dual-Layer OS Abstraction.} Normalized fields + OS-native opaque blob.
\item \textbf{Dual Acquisition Modes.} Analysis mode for research; Investigation mode for forensic investigations.
\item \textbf{Confidentiality.} Full-container AEAD encryption with post-quantum key encapsulation.
\end{enumerate}

Capture-time blocks are optimized for streaming, append-only acquisition. The Structural namespace (\hex{1000}--\hex{1FFF}) holds derived views of the capture---virtual address maps, seek tables, pointer graphs---that enable efficient random access. Such blocks are written either at capture time (before the End-of-Capture block) or afterwards in extension segments (Section~\ref{sec:extsegments}), which leave the capture segment byte-for-byte untouched.

\subsection{Scope of the Integrity Guarantee}\label{sec:integrityscope}
The hash chain provides \emph{tamper detection}, not \emph{tamper resistance}. It protects against \textbf{accidental corruption} and detects \textbf{naive modification}, including block reordering, insertion, and deletion---threats that a per-block checksum alone cannot detect, since the chain cryptographically binds each block to its predecessor and ultimately to the file header. For tamper evidence admissible in legal contexts, producers \SHOULD{} complement the hash chain with external mechanisms (digital signature over \field{FileHash}, RFC~3161 timestamp, write-once media). When encryption is active, the AEAD tag provides stronger integrity. The hash chain alone \MUSTNOT{} be represented as providing forensic-grade tamper evidence.

\begin{table}[H]\centering\caption{Integrity mechanisms: guarantees and limitations.}\label{tab:threatmodel}\small

\begin{notebox}[title={BlockCount semantics}]
\field{BlockCount} counts the blocks of the capture segment, including the End-of-Capture block; blocks in extension segments (Section~\ref{sec:extsegments}) are never counted. A producer that does not know the count when it writes the header (streaming acquisition) \MUST{} write \hex{00000000} and \MUSTNOT{} patch the field afterwards: the header is covered by Block~0's \field{PrevHash} and by the EoC \field{FileHash}, so a later modification (except the one-time \field{CipherLen} patch, Section~\ref{sec:streamenc}) would invalidate both. Such a producer \SHOULD{} record the exact count in the EoC block's \field{BlockCount} field instead (Table~\ref{tab:eoc}). Encrypted containers \MAY{} leave the header field zero and rely on the (encrypted) EoC count. Every non-zero count---header or EoC---\MUST{} equal the number of capture-segment blocks actually parsed, including the EoC block; otherwise the file \MUST{} be considered truncated or corrupt (consumer rule~13, Section~\ref{sec:conformance}).
\end{notebox}

\subsection{Byte Order}
All multi-byte structural integers are little-endian (\field{Endianness}=\hex{01}). Memory content within \field{PageData} is stored in the target architecture's native order. See Section~\ref{sec:byteorder} for the complete byte-order domain summary.

\subsection{Version Compatibility}\label{sec:versioncompat}
Unknown major version: \SHOULD{} reject. Unknown minor of a known major: \MUST{} parse; minor revisions only add block types, reserved-field semantics, and optional structures, all of which a consumer of an earlier minor skips by the usual rules (unknown block types via \field{BlockLength}, reserved fields ignored). Files that use any feature introduced in version~1.1 (extension segments, EoC \field{BlockCount}, \field{HashAlgo}, Thread Context, VAS Map \field{NameSource}, blocks \hex{0054} and \hex{0059}--\hex{005B}, page state NotResident) \SHOULD{} set \field{Version} to \hex{0101}; files written as \hex{0100} remain valid. Patch revisions (e.g., 1.1.1) do not change \field{Version}, which stays \hex{0101} (there is no patch byte); they correct errata and define semantics for reserved fields whose zero value preserves the prior meaning. A 1.1.0 consumer computes the AAD over the unzeroed header and therefore cannot decrypt files with \field{CipherLen}$\neq$0 (Section~\ref{sec:enclayout}); files with \field{CipherLen}=0 are unaffected. A consumer whose tag verification fails on such a file \SHOULD{} report that it may require 1.1.1 support rather than tampering (Section~\ref{sec:enclayout}). Always use \field{HeaderSize} to locate Block~0.

\section{Block Architecture}\label{sec:blocks}
%% ======================================================================
Every block consists of a \textbf{fixed 80-byte Common Block Header} followed by a \textbf{variable-length payload}. \field{BlockLength} specifies the total \textbf{on-disk} size of the block (header + payload, in compressed form if applicable). Consumers \MUST{} verify $\field{BlockLength} \geq 80$ and \MUST{} reject blocks that violate this constraint. Unknown types are skipped via \field{BlockLength}.

\subsection{Common Block Header (80 bytes)}\label{sec:blockheader}

When the \field{Compressed} flag is set, only the payload portion (bytes after the 80-byte Common Block Header) is compressed. The on-disk compressed payload is structured as follows:

\subsection{Integrity Chain (\field{PrevHash})}\label{sec:hashchain}
The integrity hash algorithm is selected by the \field{HashAlgo} field in the file header (Table~\ref{tab:fileheader}). All integrity fields within a single file---\field{PrevHash}, EoC \field{FileHash}, End-of-Extension \field{SegmentHash}, and Module Entry \field{DiskHash}---\MUST{} use the same algorithm; producers \MUSTNOT{} mix algorithms within a file. All registered algorithms produce a 32-byte output, so field layouts are independent of the selection.

Let $H(\cdot)$ denote the selected algorithm. Then:
\begin{itemize}[leftmargin=1.5em, itemsep=2pt]
\item \textbf{Block 0:} $\field{PrevHash} = H(\text{File Header, all \field{HeaderSize} bytes})$.
\item \textbf{Block $i$ ($i\geq 1$):} $\field{PrevHash} = H(\text{Block}_{i-1})$. The chain continues across the End-of-Capture block into extension segments (Section~\ref{sec:extsegments}).
\end{itemize}

\noindent\textbf{Default and rationale.} \field{HashAlgo}=\hex{00} (BLAKE3) is \textbf{RECOMMENDED} for general use and is the default for all implementations. Producers \SHOULD{} select \hex{01} (SHA-256) or \hex{02} (SHA-512/256) only when FIPS~140 compliance, ecosystem interoperability, or organizational policy requires a NIST-standardized hash; or when platform measurements indicate a NIST hash outperforms BLAKE3---for example, aarch64 systems with the ARMv8 Cryptographic Extension, where SHA-256 hardware acceleration can outperform software BLAKE3.

\noindent\textbf{Scope of selection.} The \field{HashAlgo} selection applies only to integrity hashing: \field{PrevHash}, \field{FileHash}, \field{SegmentHash}, and \field{DiskHash}. The key derivation function defined in Section~\ref{sec:kem} always uses HKDF-BLAKE3 regardless of \field{HashAlgo}; integrity hashing and key derivation are independent design choices and are not configured together.

\noindent\textbf{Interpretation of references.} Where this specification refers to ``\blake{}'' in integrity contexts---\field{PrevHash} (this section), \field{FileHash} (Section~\ref{sec:eoc}), \field{SegmentHash} (Section~\ref{sec:extsegments}), and \field{DiskHash} (Section~\ref{sec:modentry})---the reference denotes the algorithm selected by \field{HashAlgo}. References to HKDF-\blake{} (Section~\ref{sec:kem}) are not subject to \field{HashAlgo} and always denote BLAKE3.

\noindent\textbf{Scope of hashing.} Hashes cover raw on-disk bytes (compressed form if applicable). When \field{Encrypted} is set, all \field{PrevHash} fields \MUST{} be zero (Section~\ref{sec:enc-integrity}).


\subsection{End-of-Capture Block (\hex{0FFF})}\label{sec:eoc}
Completeness marker. An acquirer \SHOULD{} emit it as the final block of the capture segment. A verified EoC block \MAY{} be followed by extension segments (Section~\ref{sec:extsegments}); bytes after the last verified segment are non-MSL trailing data.

\noindent Version~1.0.0 defined bytes \texttt{+0x28}--\texttt{+0x2F} as reserved (zero), which reads as $\field{BlockCount}=0$; some 1.0.0 producers wrote a 40-byte payload without them. Consumers \MUST{} accept a 40-byte EoC payload and treat its count as unknown.

\subsection{Extension Segments and End-of-Extension Block (\hex{0FFE})}\label{sec:extsegments}
An MSL file consists of the file header, exactly one \textbf{capture segment}, and zero or more \textbf{extension segments}, in this order (Figure~\ref{fig:ext-layout}). The capture segment is the evidence: everything from Block~0 through the End-of-Capture block, exactly as the acquirer or importer wrote it. An extension segment is a run of one or more blocks terminated by an End-of-Extension block (\hex{0FFE}). Extension segments let producers other than the acquirer---enrichment tools, analysis frameworks, importers preserving third-party annotations---add blocks after the capture has completed, without rewriting or re-hashing the capture segment and without patching the header. Each segment is self-delimiting and self-verifying, so a file remains usable if an appending tool is interrupted.

\noindent\textbf{Permitted block types.} Extension segments carry derived or supplementary data, never evidence. The following types \MUSTNOT{} appear in an extension segment: Memory Region (\hex{0001}), Module Entry (\hex{0002}), \hex{0010}--\hex{0015}, Import Provenance (\hex{0030}), Process Identity (\hex{0040}), \hex{0050}--\hex{0058}, and End-of-Capture (\hex{0FFF}). Permitted types are Key Hint (\hex{0020}), Related Dump (\hex{0041}), \hex{0059}--\hex{005B} (Sections~\ref{sec:physmap}--\ref{sec:omission}), and the Structural namespace (\hex{1000}--\hex{1FFF}). Block types whose payload this specification does not define (e.g., Pointer Graph \hex{1003}, producer-defined Structural types) \MAY{} appear only in extension segments. Blocks in an extension segment \MAY{} reference blocks in the capture segment or in earlier segments by \field{ParentUUID} or payload-embedded UUID (Section~\ref{sec:crossref}).

\noindent\textbf{Producer rules.} A producer appending an extension segment \MUSTNOT{} modify any byte of the header, the capture segment, or an existing segment; \MUST{} terminate every segment it writes with an End-of-Extension block; \MUST{} continue the \field{PrevHash} chain from the last block already in the file (zero when encrypted); and \MUST{} write the exact \field{BlockCount} and \field{SegmentHash}. A producer that finds trailing data after the last verified segment \SHOULD{} refuse to append rather than build on unverified bytes. In an encrypted container, extension segments written before sealing \MUST{} lie inside the primary AEAD ciphertext, i.e., be written before the AEAD is finalized; after sealing, a producer \MUST{} append only sealed extension segments (Section~\ref{sec:sealedseg}).

\noindent\textbf{Consumer rules.} After parsing and verifying the EoC block (and, when encrypted, the AEAD tag), a consumer \MUST{} attempt to parse extension segments: read blocks until an End-of-Extension block, then verify (a)~chain continuity from the preceding block (unencrypted files), (b)~\field{SegmentHash}, and (c)~\field{BlockCount}. Only a segment that passes all three checks is a \emph{verified segment}; its blocks \MAY{} then be presented alongside the capture. A segment that fails verification or is not terminated---EOF, non-magic bytes, or a block that fails framing before an End-of-Extension block is found---\MUSTNOT{} be presented as verified, and everything from its first byte to EOF is trailing data. Consumers that do not implement extension segments \MUST{} treat everything after the EoC block as trailing data (consumer rule~14, Section~\ref{sec:conformance}). In an encrypted container, bytes after the primary AEAD tag are parsed as sealed extension segments (Section~\ref{sec:sealedseg}) before the remainder is treated as trailing data.

\subsection{Thread Context (\hex{0011})}\label{sec:threadctx}
A Thread Context block records the execution state of a single thread of the target process at acquisition time: the thread identifier, scheduling state, an optional thread name, and a register file. One block is emitted per captured thread. These blocks let a consumer reconstruct the CPU state required to emulate or single-step execution forward from the captured memory image. Thread Context blocks are \OPTIONAL; their presence is advertised by the \field{ThreadContexts} bit (bit~2) in \field{CapBitmap}. \field{ParentUUID} \MAY{} reference the Process Identity block (\hex{0040}) or be zero.

Thread Context is an evidence block: it \MUST{} be written in the capture segment (never in an extension segment, Section~\ref{sec:extsegments}) and \SHOULD{} precede the first Memory Region block so that consumers know the thread set before they classify regions (Section~\ref{sec:blockordering}).

Exactly one Thread Context block in a file \SHOULD{} set the \field{Current} flag, identifying the thread whose register file---in particular its program counter---represents the natural resumption point for emulation. If no block sets \field{Current}, consumers \SHOULD{} treat the first Thread Context block in file order as current.

\subsection{VAS Map (\hex{1001})}\label{sec:vasmap}
A VAS Map records the target's enumerated virtual address space as a list of ranges with protection, type, and mapped path---one entry per range the acquirer enumerated, whether or not its bytes were captured. It is the only block from which a consumer can tell which parts of the address space existed but were not stored. Although it is a Structural-namespace block (Section~\ref{sec:typeregs}), an acquirer \MAY{} write it at capture time; the \textbf{RECOMMENDED} position is immediately before the End-of-Capture block, after all Memory Region and Module Entry blocks. An analysis tool \MAY{} instead add it in an extension segment (Section~\ref{sec:extsegments}). When a file contains several VAS Maps, the last one in file order supersedes earlier ones. \field{ParentUUID} is zero.

\subsection{Physical Memory Map (\hex{0059})}\label{sec:physmap}
A Physical Memory Map records the host's physical address ranges (e.g., the top-level entries of Linux \texttt{/proc/iomem}: ``System RAM'', ``Reserved'', PCI windows) at acquisition time. It gives analysis tools that correlate a process capture with a physical memory image the layout they need to translate addresses. The block is \OPTIONAL{} and is defined here so that the type code and layout are stable; it is not yet emitted by any known producer. It \MAY{} be written in the capture segment or in an extension segment (Section~\ref{sec:extsegments}). \field{ParentUUID} is zero.

\subsection{Module Build-ID Manifest (\hex{005A})}\label{sec:buildid}
A Module Build-ID Manifest supplements the Module Entry blocks of a capture with build identifiers (ELF \texttt{NT\_GNU\_BUILD\_ID}, PE CodeView GUID+age, Mach-O \texttt{LC\_UUID}) and on-disk hashes that were not available---or not yet computed---when the acquirer wrote the module list. It is written by enrichment tools, either in the capture segment or in an extension segment (Section~\ref{sec:extsegments}). Readers merge rows into the module list by matching \field{BaseAddr} against Module Entry \field{BaseAddr}; a non-zero \field{DiskHash} in a row supersedes an all-zero \field{DiskHash} in the matching Module Entry. Rows whose \field{BaseAddr} matches no Module Entry \SHOULD{} be reported as dangling (Section~\ref{sec:crossref}) but \MUSTNOT{} be discarded. \field{ParentUUID} is zero.

\subsection{Region Omission Manifest (\hex{005B})}\label{sec:omission}
A Region Omission Manifest lists the address ranges that the acquirer \emph{deliberately} did not capture---because of a region scope selection (e.g., heap and stack only) or module exclusion patterns---so that a consumer can distinguish a partial capture from an incomplete one. Omitted ranges are absent from the Memory Region stream but present in the VAS Map (Section~\ref{sec:vasmap}); this block records the reason. A producer \MUST{} emit it only when at least one range was omitted, and \MAY{} write it in the capture segment or in an extension segment (Section~\ref{sec:extsegments}). \field{ParentUUID} is zero.

Unlike the general convention of Section~\ref{sec:encoding}, the strings in this block carry \textbf{no terminating NUL}: every length field counts UTF-8 bytes only, and each string is zero-padded to an 8-byte boundary.

\section{Investigation Mode}\label{sec:investigation}
%% ======================================================================
When \field{Investigation} (bit~1) is set, the acquirer \MUST{} capture system-wide context alongside per-process memory: acquisition operator, system hostname, and system-wide tables (process list, network connections, open handles). When not set, the acquisition is in Analysis mode and \MUST{} follow Figure~\ref{fig:acq-sequence}.

\subsection{Block Ordering}\label{sec:blockordering}
\begin{enumerate}[leftmargin=1.8em, itemsep=2pt]
\item \textbf{Block~0:} Process Identity (\hex{0040}).
\item \textbf{Block~1:} Module List Index (\hex{0010}).
\item \textbf{Block~2:} System Context (\hex{0050}) --- \REQUIRED.
\end{enumerate}
System-wide table blocks (\hex{0051}--\hex{0053}) follow with \field{ParentUUID} referencing the System Context block; a Connectivity Table (\hex{0054}, Section~\ref{sec:block:connectivity-table}) \MAY{} follow them with \field{ParentUUID} zero. \subsection{Connectivity Table (\hex{0054})}
\label{sec:block:connectivity-table}

The Connectivity Table records kernel network state that has no
socket-endpoint representation and therefore does not fit the schema of the Connection Table block (\texttt{0x0052}). The two blocks are complementary: endpoints with process attribution remain in the Connection Table, while routing entries, neighbour-discovery (ARP) caches, raw packet sockets, per-interface counters, aggregate socket-family statistics, and Management Information Base (MIB) counters are recorded here. The separation allows downstream analyzers to distinguish the two forensic questions of \emph{who} was connected to \emph{what} and \emph{what was the network state at capture time}. The
latter is essential for detecting raw-socket observers whose presence is invisible to the conventional socket table, because they possess neither an address nor a port tuple.

The block is emitted only in Investigation mode; its presence is advertised by \field{TableBitmap} bit~3 (Table~\ref{tab:sysctx-bitmap}). Unlike \hex{0051}--\hex{0053}, \field{ParentUUID} is zero. The payload is a heterogeneous tagged-row table. Each row begins with a one-byte row-type discriminator, followed by a two-byte row length and a row-type-specific body. Seven row shapes are defined; readers that do not recognize a row type advance by \texttt{RowLen} bytes.

\begin{table}[H]\centering\caption{Connectivity Table payload.}\label{tab:block:ct}\small
\begin{tabular}{M M l l p{5.5cm}}\toprule\textbf{Off}&\textbf{Size}&\textbf{Field}&\textbf{Abbr}&\textbf{Description}\\\midrule
+0x00 & 4   & \field{RowCount} & RC  & Total number of rows across all row types. \\
+0x04 & 4   & \field{Reserved} & R   & Zero. \\
+0x08 & var & \field{Rows}     & --- & Concatenation of tagged rows (see Table~\ref{tab:block:ct-rows}). \\\bottomrule
\end{tabular}\end{table}

Each row is prefixed by \texttt{RowType(1)\,RowLen(2)} and followed by
\texttt{RowLen} bytes of row-specific body (\texttt{RowLen} excludes the
3-byte prefix). Rows are packed back to back without internal padding;
only the payload as a whole is padded to an 8-byte boundary. The defined
row types are enumerated in Table~\ref{tab:block:ct-rows}. String-typed
fields within row bodies use a two-byte length prefix followed by
\texttt{Len} bytes of UTF-8 content (no NUL). All multi-byte integers are
little-endian. IPv4 addresses are carried as four raw bytes in network
order; IPv6 addresses as sixteen raw bytes. Row \hex{07} stores
\texttt{Value} as an unsigned 8-byte field; counters the kernel reports as
signed (e.g., \texttt{Tcp.MaxConn}~=~$-1$) are written in two's complement
so that the evidence survives verbatim.

\subsection{Redaction and Data Minimization}\label{sec:redaction}
Investigation-mode fields such as \field{AcqUser}, \field{Hostname}, \field{Domain}, and \field{CaseRef} may contain personally identifiable information or data subject to disclosure restrictions. This section provides guidance for producers that must balance forensic completeness with privacy requirements.

\begin{itemize}[leftmargin=1.5em, itemsep=2pt]
\item Producers \MAY{} emit zero-length strings (Len=0) for \field{AcqUser}, \field{Domain}, and \field{CaseRef} when organizational policy requires data minimization. A conformant consumer \MUST{} handle zero-length optional strings gracefully.
\item When any field has been intentionally stripped or pseudonymized, producers \MUST{} set the \field{Redacted} flag (bit~3) in the file header. This distinguishes intentional redaction from fields that were merely unavailable at acquisition time: a zero-length string with \field{Redacted}=0 means ``not captured''; the same string with \field{Redacted}=1 means ``captured but removed.''
\item When sharing MSL files for research or cross-organizational analysis, producers \SHOULD{} strip or pseudonymize personally identifiable fields prior to distribution and set the \field{Redacted} flag.
\item \field{Hostname} and \field{OSDetail} carry forensic value that may be essential for investigation continuity. Redaction of these fields \SHOULD{} be documented in the case log.
\end{itemize}

\section{Encryption}\label{sec:encryption}
%% ======================================================================

\subsection{Scope}
When the \field{Encrypted} flag (bit~2) is set, the entire block stream is protected by AEAD (Authenticated Encryption with Associated Data). The file header remains in cleartext for format identification. All block data---including block types, UUIDs, timestamps, module paths, and memory content---is encrypted.

Full-container encryption is chosen over per-block encryption to prevent metadata leakage: per-block schemes would expose block types, block counts, block sizes, and timing patterns, all of which can reveal forensically sensitive information (e.g., which libraries are loaded, how many memory regions exist) without the decryption key.

\subsection{Encrypted File Layout}\label{sec:enclayout}

\begin{enumerate}[leftmargin=1.8em, itemsep=2pt]
\item \textbf{File header (128\,B, cleartext):} Authenticated as Associated Data (AAD) to the AEAD. The AAD is the file header with bytes \hex{78}--\hex{7F} (\field{CipherLen}) set to zero, followed by any KEM ciphertext. Tampering causes decryption failure.
\item \textbf{KEM ciphertext (0 or variable, cleartext):} Present when \field{KeyEncap}$\neq$\hex{00}. Size is \field{KEMCtLen}. Also in AAD (item~1).
\item \textbf{Encrypted block stream:} AEAD ciphertext of Block~0 through EoC, followed by any extension segments (Section~\ref{sec:extsegments}). Its length is \field{CipherLen} when non-zero. The only encrypted region of the primary AEAD.
\item \textbf{AEAD authentication tag (16\,B, not encrypted):} Output of the AEAD. Required for decryption. Requires the symmetric key. Immediately follows the ciphertext.
\item \textbf{Sealed extension segments (optional, cleartext header + ciphertext + tag):} Only when \field{CipherLen}$\neq$0 (Section~\ref{sec:sealedseg}).
\end{enumerate}

\noindent\textbf{Locating the tag.} When \field{CipherLen}=0 (all 1.1.0 files, and non-seekable streaming producers, Section~\ref{sec:streamenc}), the tag is the final 16 bytes of the file; such a file cannot carry sealed segments or trailing data. When \field{CipherLen}$\neq$0, the ciphertext occupies [\field{HeaderSize}+\field{KEMCtLen}, \field{HeaderSize}+\field{KEMCtLen}+\field{CipherLen}) and the tag immediately follows it; sealed extension segments (Section~\ref{sec:sealedseg}), then trailing data, follow the tag. Consumers \MUST{} reject \field{CipherLen} $>$ file size $-$ \field{HeaderSize} $-$ \field{KEMCtLen} $-$ 16. \field{CipherLen} lies outside the AAD, but changing it moves the tag boundary and thus changes the authenticated ciphertext and the tag bytes; verification then fails except with negligible probability. A consumer that fails tag verification on a file whose bytes \hex{78}--\hex{7F} are non-zero \SHOULD{} report that the file may require 1.1.1 support rather than reporting tampering. For \field{CipherLen}=0 the AAD is byte-identical to the 1.1.0 AAD.

\noindent\textbf{Extension segments in encrypted containers.} Extension segments written before sealing \MUST{} lie inside the primary AEAD ciphertext, i.e., they are written before the AEAD is finalized, and the primary tag covers them. Enrichment after sealing appends sealed extension segments (Section~\ref{sec:sealedseg}), each separately authenticated and chained to the preceding tag; it requires the CEK and \field{CipherLen}$\neq$0. Bytes after the primary tag that are not verified sealed segments are trailing non-MSL data.

\noindent\textbf{Chain-of-custody without the key.} Producers \SHOULD{} record an external hash of the complete file at acquisition time (\blake{} or SHA-256, offset~0 to EOF), computed after the \field{CipherLen} patch, i.e., over the final file. This digest \SHOULD{} be stored in the case evidence log, not in the file.

\noindent Both ciphers provide 256-bit keys. AES-256 and ChaCha20 are post-quantum safe at the symmetric level (Grover reduces effective key strength by half: AES-256 $\to$ 128-bit equivalent). The post-quantum vulnerability lies in key \emph{encapsulation}, addressed below.

\subsection{Key Encapsulation}\label{sec:kem}
The \field{KeyEncap} field specifies how the content encryption key (CEK) was protected. After KEM decapsulation, the shared secret is passed through HKDF-\blake{} (salt=\field{DumpUUID}, info=\texttt{"MSL-CEK-v1"}) to derive the 256-bit CEK.

\begin{table}[H]\centering\caption{Key encapsulation mechanisms.}\label{tab:kem}\small
\begin{tabular}{M l l p{4.5cm}}\toprule\textbf{Code}&\textbf{Mechanism}&\textbf{Ct Size}&\textbf{Notes}\\\midrule
0x00 & None & 0 & Raw key (passphrase or external). \\
0x01 & X25519 & 32\,B & Classical ECDH. \\
0x02 & ML-KEM-768 & 1088\,B & FIPS~203~\cite{mlkem}. NIST PQ standard. \\
0x03 & ML-KEM-1024 & 1568\,B & FIPS~203. Higher margin. \\
0x04 & X25519+ML-KEM-768 & 1120\,B & Hybrid. \textbf{Recommended.} \\
0x05--0xFE & \textit{Reserved} & --- & \\
0xFF & Other & var & Non-standard. \\\bottomrule
\end{tabular}\end{table}

\begin{notebox}[title={Operational model: symmetric key vs.\ KEM}]
The symmetric cipher always encrypts the data. \field{KeyEncap} determines how the CEK reaches the intended recipient:
\begin{itemize}[leftmargin=1.5em, itemsep=2pt]
\item \textbf{\field{KeyEncap}=\hex{00} (passphrase/raw key):} The responder provides a passphrase or externally managed key. Suitable for single-operator scenarios.
\item \textbf{\field{KeyEncap}$\neq$\hex{00} (KEM):} The acquirer encrypts to the organization's public key. The responder need not know any secret. The private key is held by the analysis team or in an HSM. This provides separation of duties: the responder who captures evidence cannot decrypt it.
\item \textbf{Passphrase + KEM (dual control):} Both the responder's passphrase and the organization's private key are required, preventing either party from accessing evidence alone.
\end{itemize}
\noindent The post-quantum options protect against ``harvest now, decrypt later'' attacks.
\end{notebox}

\noindent\textbf{Hybrid X25519 + ML-KEM-768.} The recommended hybrid scheme (\hex{04}) concatenates shared secrets from X25519 and ML-KEM-768 before KDF, ensuring the file remains secure as long as \emph{either} assumption holds. This concatenate-then-KDF construction follows the approach analyzed by Bindel et al.~\cite{bindel2019} and adopted by TLS~1.3 hybrid key exchange~\cite{ietfhybrid}. The hybrid mode is the \textbf{recommended} setting for Investigation mode captures.

\subsection{Key Derivation}
\begin{description}[style=nextline, leftmargin=2em, itemsep=3pt]
\item[\hex{00} --- None] 256-bit CEK provided externally. KDF fields are zero.
\item[\hex{01} --- Argon2id] Passphrase-derived. Minimum: time=3, memory=65536\,KiB, lanes=4.
\end{description}

\noindent Because \field{KDFSalt} is generated uniquely per file (16 random bytes), the same passphrase produces a different CEK for each capture, eliminating nonce-reuse risk even when nonces are generated independently across files.

\subsection{Interaction with the Integrity Chain}\label{sec:enc-integrity}
When \field{Encrypted} is set:
\begin{itemize}[leftmargin=1.5em, itemsep=2pt]
\item \field{PrevHash}: \MUST{} be zero in every block, in the capture segment and in extension segments. AEAD authenticates atomically.
\item EoC \field{FileHash} and End-of-Extension \field{SegmentHash}: \SHOULD{} be computed over plaintext (enables post-decryption verification).
\item AAD: the file header with bytes \hex{78}--\hex{7F} (\field{CipherLen}) set to zero, followed by any KEM ciphertext.
\item Extension segments (Section~\ref{sec:extsegments}) are part of the encrypted stream; the chain-continuity check is skipped (all \field{PrevHash} zero) but \field{SegmentHash} and \field{BlockCount} are verified after decryption. Segments added after the primary tag are sealed extension segments (Section~\ref{sec:sealedseg}).
\end{itemize}

\subsection{Streaming Encryption}\label{sec:streamenc}
Producers \SHOULD{} encrypt incrementally: (1)~write the header with \field{CipherLen}=0 (or its final value, if already known), init AEAD with key, nonce, AAD; (2)~for each block, serialize, encrypt, write; (3)~after EoC and any extension segments, finalize AEAD, append 16-byte tag; (4)~if \field{CipherLen}=0 was written and the output is seekable, patch the 8 bytes at header offset \hex{78} once with the primary ciphertext length. A parallel hasher (\field{HashAlgo}) computes plaintext \field{FileHash} and \field{SegmentHash} before encryption. $O(1)$ memory.

Producers \SHOULD{} record \field{CipherLen}. Producers that know the ciphertext length before encryption begins \MAY{} write the final value directly; otherwise they write 0 and, on seekable output, patch it once after the tag. Non-seekable producers that do not know the length leave it 0. The \field{CipherLen} patch is the only permitted modification of a written header, and only the producer that seals the primary AEAD stream \MAY{} perform it; appenders (Sections~\ref{sec:extsegments} and~\ref{sec:sealedseg}) \MUSTNOT{}, and the header \field{BlockCount} is still never patched (producer rule~16). \field{FileHash} always covers the header with \field{CipherLen} zero (it is computed before any patch, and a directly written value is hashed as zero); consumers verifying \field{FileHash} \MUST{} hash bytes \hex{78}--\hex{7F} as zero.

\subsection{Sealed Extension Segments}\label{sec:sealedseg}
A sealed extension segment adds one extension segment (Section~\ref{sec:extsegments}) to an encrypted container after the primary AEAD tag has been written. Each sealed segment is a separate AEAD message under a per-segment subkey of the CEK, with its own nonce and tag, chained to the preceding tag. Sealed segments require a non-zero header \field{CipherLen} (Section~\ref{sec:enclayout}).

\begin{lstlisting}
... | Primary AEAD tag | SealHeader 1 | Ciphertext 1 | Tag 1 | ... | SealHeader m | Ciphertext m | Tag m | [trailing data]
\end{lstlisting}

\noindent Each \field{SealHeader} is 64 bytes of cleartext (Table~\ref{tab:sealhdr}), followed by \field{SegCipherLen} bytes of ciphertext and a 16-byte tag.

\begin{table}[H]\centering\caption{Sealed segment header (64 bytes).}\label{tab:sealhdr}\small
\begin{tabular}{M M l l p{5.5cm}}\toprule\textbf{Off}&\textbf{Size}&\textbf{Field}&\textbf{Abbr}&\textbf{Description}\\\midrule
+0x00 & 4  & \field{Magic}       & Mg  & \hex{4D534C53} (\magic{MSLS}). \\
+0x04 & 2  & \field{SealHdrSize} & SHS & 64. \\
+0x06 & 2  & \field{SegIndex}    & SI  & 1-based position of this sealed segment after the primary tag. \\
+0x08 & 8  & \field{SegCipherLen} & SCL & Ciphertext length in bytes. \MUST{} be $>$ 0. \\
+0x10 & 24 & \field{Nonce}       & --- & AEAD nonce, encoded as the header \field{Nonce} for \field{EncAlgo} (Table~\ref{tab:enctable}). \\
+0x28 & 24 & \field{Reserved}    & R   & Zero. \\\bottomrule
\end{tabular}\end{table}

\noindent\textbf{Size:} $4{+}2{+}2{+}8{+}24{+}24 = 64$.

\noindent\textbf{Cipher suite and key.} The cipher suite is the header \field{EncAlgo}. Segment $i$ is encrypted under $\mathit{SegKey}_i$ = HKDF-\blake{}(IKM=CEK, salt=\field{DumpUUID}, info=\texttt{"MSL-SEG-v1"} $\Vert$ LE16($i$)), the construction of Section~\ref{sec:kem}, where the CEK is the Argon2id output, the external key, or the KEM-derived CEK. \field{SegIndex} therefore ranges from 1 to 65535. \field{Nonce} \MUST{} be generated fresh from a CSPRNG for every segment; the per-segment subkey separates segment keys from the primary stream, and the fresh nonce prevents (key, nonce) reuse if a segment index is written again after a truncation.

\noindent\textbf{Associated data.} $\mathit{AAD}_i$ is the file header with bytes \hex{78}--\hex{7F} (\field{CipherLen}) set to zero, followed by any KEM ciphertext, followed by the 64-byte \field{SealHeader} of segment $i$ and the tag of segment $i{-}1$, where $\mathit{Tag}_0$ is the primary tag. This binds each segment to its position, to the exact bytes it extends, and to this file, so segments cannot be grafted onto a re-sealed copy with the same \field{DumpUUID} and passphrase (against parties without the CEK).

\noindent\textbf{Plaintext.} The plaintext is exactly one extension segment per Section~\ref{sec:extsegments}: \field{PrevHash} \MUST{} be zero, the End-of-Extension block \MUST{} end exactly at \field{SegCipherLen}, the permitted-block-type rules apply, and \field{SegmentHash} and \field{BlockCount} are verified after decryption.

\noindent\textbf{Producer rules.} A producer appending a sealed segment \MUST{} hold the CEK (in KEM mode this requires the recipient's private key, so an acquirer that only holds the public key cannot append); \MUST{} verify the primary tag and every existing sealed segment; \MUST{} refuse when the header \field{CipherLen}=0; \SHOULD{} refuse when trailing data is present; \MUSTNOT{} modify any earlier byte, including the header; and \MUST{} write the whole sealed segment (\field{SealHeader}, ciphertext, tag) as one unit.

\noindent\textbf{Consumer rules.} After the primary tag verifies, a consumer parses sealed segments in order, $i = 1, 2, \ldots$. On any failure---short read, \field{Magic} or \field{SealHdrSize} mismatch, \field{SegIndex}$\neq i$, \field{SegCipherLen} zero or exceeding the bytes remaining after the \field{SealHeader} minus 16, tag failure, or a malformed plaintext segment---everything from that segment's first byte to EOF is trailing data. A consumer \MUSTNOT{} present plaintext from a sealed segment before its tag verifies.

\noindent\textbf{Security considerations.} Dropping trailing sealed segments is undetectable, exactly as for plaintext extension segments (Section~\ref{sec:extsegments}); this is acceptable because evidence block types are forbidden in segments. Sealed segments never alter the capture segment or the primary ciphertext.

\section{Raw Dump Import}\label{sec:import}
%% ======================================================================
An MSL file may be created by importing a pre-existing raw memory dump (ELF core, Windows Minidump, ProcDump output, or plain byte stream) rather than by live acquisition. The Import Provenance block (\hex{0030}) records the origin of the imported data: the source format, the tool that performed the conversion, the original file size, and an optional free-text note. When \field{Imported} (bit~0) is set in \field{Flags}, this block \MUST{} appear as Block~0.

\section{Parsing Walkthrough}\label{sec:parsing}
%% ======================================================================
\begin{description}[style=nextline, leftmargin=2em, itemsep=4pt]
\item[Step 1:] Read 9 bytes. Verify magic. \field{Endianness} \MUST{} be \hex{01}. Read \field{HeaderSize}.
\item[Step 2:] If \field{Encrypted}: read extension (\hex{40}--\hex{7F}). If \field{KEMCtLen}$>$0, read KEM ciphertext. Obtain key. Decrypt. Continue with plaintext.
\item[Step 3:] Read blocks at \field{HeaderSize} (+\field{KEMCtLen} if encrypted) up to the EoC block. Verify \field{BlockLength} $\geq$ 80. Parse or skip via \field{BlockLength}. Verify every non-zero \field{BlockCount} (header, EoC) against the parsed capture-segment count.
\item[Step 4:] If unencrypted: verify the \field{PrevHash} chain with the algorithm selected by \field{HashAlgo}. If encrypted: locate the AEAD tag at \field{HeaderSize}+\field{KEMCtLen}+\field{CipherLen} (or at EOF$-$16 when \field{CipherLen}=0), rejecting an out-of-bounds \field{CipherLen}, and verify it.
\item[Step 5:] Verify EoC \field{FileHash} if present. Then parse extension segments (Section~\ref{sec:extsegments}): verify chain continuity, \field{SegmentHash}, and \field{BlockCount} of each. If encrypted and \field{CipherLen}$\neq$0, then parse sealed extension segments after the tag (Section~\ref{sec:sealedseg}). The remainder is trailing data.
\item[Step 6:] \field{Investigation}? Expect Block~2 = System Context.
\item[Step 7:] \field{Imported}? Read Import Provenance.
\end{description}

\section{Conformance}\label{sec:conformance}
%% ======================================================================
\subsection{Producer}
A conformant producer \MUST: (1) write valid header with \field{Magic}, \field{Endianness}={}\allowbreak\hex{01}, \field{HeaderSize}, \field{Version}; (2) generate UUIDv4 in RFC~9562 binary layout; (3) compute \field{PrevHash} with the selected \field{HashAlgo} (zero when encrypted); (4) set reserved fields to zero; (5) pad8 all variable fields; (6) never modify written blocks; (7) set \field{CapBitmap} accurately; (8) if importing: set \field{Flags} bit~0, emit Import Provenance as Block~0; (9) set \field{PayloadVersion} to~1; (10) set \field{CompAlgo} bits to 00 when uncompressed; (11) split regions exceeding $2^{32}{-}81$ bytes; (12) write 32 zero bytes for unavailable \field{DiskHash}; (13) reject \field{PageSizeLog2} outside $[10,40]$; (14) emit well-formed UTF-8 per RFC~3629 for all string fields; (15) convert port numbers from network byte order to little-endian before writing; (16) set the header \field{BlockCount} to the number of capture-segment blocks including EoC, or to zero when unknown at header-write time, and never patch it afterwards; record the exact count in the EoC \field{BlockCount} field.

A conformant acquirer \MUST{} emit Process Identity as Block~0 and Module List Index as Block~1.

\noindent\textbf{Investigation:} (17) emit System Context as Block~2; (18) set \field{CapBitmap} bit~11; (19) set \field{TableBitmap}; (20) set \field{Redacted} flag (bit~3) when any field has been intentionally stripped or pseudonymized.

\noindent\textbf{Encryption:} (21) \field{HeaderSize}=128; (22) valid encryption extension; (23) AEAD with header (+KEM ct) as AAD, bytes \hex{78}--\hex{7F} zeroed (Section~\ref{sec:enclayout}); (24) append 16-byte tag immediately after the ciphertext, and append after it only sealed extension segments (Section~\ref{sec:sealedseg}); (25) zero all \field{PrevHash}; (26) \field{Nonce} from CSPRNG; (27) KEM ciphertext after header when \field{KeyEncap}$\neq$\hex{00}.

\noindent\textbf{Compression:} (28) when \field{Compressed} is set, write 8-byte \field{UncompressedSize} before compressed data; (29) set \field{BlockLength} to on-disk size.

\noindent\textbf{Block types:} (30) \MUSTNOT{} emit block types whose payload format is not yet specified in this document, except producer-defined Structural types inside extension segments (Section~\ref{sec:extsegments}).

\noindent\textbf{Hash algorithm:} (31) set \field{HashAlgo} to a registered code from Table~\ref{tab:hashalgos}; the default (\hex{00}, BLAKE3) \SHOULD{} be used unless FIPS compliance, organizational policy, or platform performance measurements indicate otherwise; (32) use the selected algorithm exclusively for all \field{PrevHash}, \field{FileHash}, \field{SegmentHash}, and \field{DiskHash} computations within the file; \MUSTNOT{} mix algorithms within a single file.

\noindent\textbf{Extension segments:} (33) when appending, \MUSTNOT{} modify any byte of the header, the capture segment, or an existing extension segment; (34) terminate every extension segment with an End-of-Extension block carrying the exact \field{SegmentHash} and \field{BlockCount}; (35) continue the \field{PrevHash} chain from the last block already in the file (zero when encrypted); (36) emit only the block types Section~\ref{sec:extsegments} permits in extension segments; (37) in encrypted containers, write extension segments inside the AEAD stream before the tag; after the tag, append only sealed extension segments (Section~\ref{sec:sealedseg}).

\noindent\textbf{Thread Context:} a producer that captures thread register state \SHOULD{} emit one Thread Context block (\hex{0011}) per thread, set the \field{Current} flag on exactly one of them, set \field{CapBitmap} bit~2, and include at least the program-counter and stack-pointer registers (Section~\ref{sec:threadctx}). (38) Thread Context blocks \MUST{} be written in the capture segment and \SHOULD{} precede the first Memory Region; (39) set \field{Suspended} only for registers read from a stopped thread and \field{Partial} whenever the register file is incomplete.

\noindent\textbf{Ciphertext length:} (40) write \field{CipherLen} either as its final value or as 0; when 0 is written and the output is seekable, the sealing producer \MAY{} patch it once after the tag (Section~\ref{sec:streamenc}); no other party patches it.

\noindent\textbf{Sealed extension segments:} (41) when appending after the primary tag, write only sealed extension segments per Section~\ref{sec:sealedseg}: hold the CEK, verify the primary tag and every existing sealed segment, refuse when the header \field{CipherLen}=0, use $\mathit{SegKey}_i$ with a fresh CSPRNG \field{Nonce}, write each segment as one unit, and never modify earlier bytes.

\noindent\textbf{Register names:} (42) name Thread Context registers per Table~\ref{tab:regnames} for the architectures it lists, and never write aliases (ARM64 \texttt{fp}/\texttt{lr}; ARM32 \texttt{r13}--\texttt{r15}).

\noindent A producer \SHOULD{} emit an EoC block. \field{FileHash} \SHOULD{} be computed over plaintext even when encrypted. When encrypted, the producer \SHOULD{} record an external file hash for chain-of-custody.

\subsection{Consumer}
A conformant consumer \MUST: (1) reject invalid magic or \field{Endianness} $\neq$ \hex{01}; (2) use \field{HeaderSize} to locate blocks; (3) skip unknown types via \field{BlockLength}; (4) reject $\field{BlockLength} < 80$; (5) detect end-of-blocks; (6) ignore reserved fields; (7) reject type \hex{0000}; (8) skip unrecognized \field{PayloadVersion} for known block types with a logged warning indicating which block types were affected; (9) treat all-zero \field{DiskHash} as unavailable; (10) reject \field{PageSizeLog2} outside $[10,40]$; (11) use explicit length fields to determine string extent, not NUL-scanning beyond the declared length; (12) preserve raw bytes for malformed UTF-8 fields and not reject the entire block; (13) verify that every non-zero block count---header \field{BlockCount} and EoC \field{BlockCount}---equals the number of capture-segment blocks parsed including the EoC block, and otherwise report the file as truncated or corrupt; accept a 40-byte EoC payload as count unknown; (14) after a verified EoC block (and, when encrypted, the primary AEAD tag), attempt to parse extension segments per Section~\ref{sec:extsegments} and, when \field{CipherLen}$\neq$0, sealed extension segments per Section~\ref{sec:sealedseg}, and treat everything after the last verified segment as trailing non-MSL data.

\noindent\textbf{Encryption:} (15) verify \field{HeaderSize}=128; read KEM ct; decrypt via AEAD with AAD (with \field{CipherLen} zeroed, Section~\ref{sec:enclayout}); reject on failure; (16) skip \field{PrevHash} verification.

\noindent\textbf{Investigation:} (17) expect Block~2 = System Context; check \field{TableBitmap}; (18) when \field{Redacted} is set, interpret zero-length optional strings as intentionally redacted rather than absent.

\noindent\textbf{Compression:} (19) read 8-byte \field{UncompressedSize} before inflating; (20) reject if decompressed size does not match \field{UncompressedSize}.

\noindent\textbf{Cross-references:} (21) log and continue on dangling \field{ParentUUID} or payload-embedded UUID references; treat the affected block as an orphan but \MUSTNOT{} discard it.

\noindent\textbf{Hash algorithm:} (22) \MUST{} implement at minimum \field{HashAlgo}={}\allowbreak\hex{00} (BLAKE3) and \field{HashAlgo}={}\allowbreak\hex{01} (SHA-256); \MAY{} implement \hex{02} (SHA-512/256) and other registered codes; \MUST{} reject files whose \field{HashAlgo} the consumer does not implement, emitting a diagnostic indicating the unsupported algorithm code.

\noindent\textbf{Extension segments:} (23) verify chain continuity from the EoC block (unencrypted files), \field{SegmentHash}, and \field{BlockCount} of every extension segment, and \MUSTNOT{} present an unterminated or failing segment as verified; (24) accept Structural and producer-defined block types in verified segments, skipping unrecognized payloads via \field{BlockLength}; (25) honour the last VAS Map in file order (Section~\ref{sec:vasmap}) and merge Module Build-ID Manifest rows by \field{BaseAddr} (Section~\ref{sec:buildid}).

\noindent\textbf{Page states:} (26) decode \field{PageStateMap} value \texttt{11} as NotResident (a zero-content page, Section~\ref{sec:threestate}), never as a read failure.

\noindent\textbf{Ciphertext length:} (27) locate the AEAD tag at EOF$-$16 when \field{CipherLen}=0, otherwise at \field{HeaderSize}+\field{KEMCtLen}+\field{CipherLen}; reject \field{CipherLen} $>$ file size $-$ \field{HeaderSize} $-$ \field{KEMCtLen} $-$ 16 (Section~\ref{sec:enclayout}).

\noindent\textbf{Sealed extension segments:} (28) verify sealed segments in order per Section~\ref{sec:sealedseg}; \MUSTNOT{} present plaintext from a sealed segment before its tag verifies; treat everything from the first failing segment to EOF as trailing data.

\noindent\textbf{Register names:} (29) \SHOULD{} normalise ARM64 \texttt{fp}$\to$\texttt{x29} and \texttt{lr}$\to$\texttt{x30} in Thread Context blocks written by 1.1.0 producers.

\noindent A consumer \SHOULD: verify the \field{PrevHash} chain when unencrypted; verify EoC \field{FileHash} after decryption.

\section{Revision History}\label{sec:revhistory}
%% ======================================================================
\noindent\textbf{1.1.1 --- 2026-10-23.} Patch revision; the header \field{Version} remains \hex{0101} (Section~\ref{sec:versioncompat}).
\begin{itemize}[leftmargin=1.5em, itemsep=3pt]
\item \textbf{\field{CipherLen}} (header offset \hex{78}, formerly \field{Reserved3}; Sections~\ref{sec:enchdr}, \ref{sec:enclayout}, \ref{sec:streamenc}): byte length of the primary AEAD ciphertext. The AAD is now the file header with bytes \hex{78}--\hex{7F} (\field{CipherLen}) set to zero, followed by any KEM ciphertext; for \field{CipherLen}=0 it is byte-identical to the 1.1.0 AAD. Producers write the final value or 0; a seekable sealing producer that wrote 0 patches it once after the tag, the only permitted header patch. A 1.1.0 consumer cannot decrypt files with \field{CipherLen}$\neq$0; files with \field{CipherLen}=0 are unaffected. Producer rules 23, 24, 40; consumer rule~27.
\item \textbf{Sealed extension segments} (Section~\ref{sec:sealedseg}, Table~\ref{tab:sealhdr}): an encrypted container can be enriched after sealing by appending AEAD segments under per-segment HKDF-\blake{} subkeys of the CEK, each with a 64-byte \field{SealHeader} (ciphertext length \field{SegCipherLen}, nonce) and its own tag, chained to the preceding tag; requires a non-zero header \field{CipherLen}. Replaces the 1.1.0 rule that nothing may be appended after the tag. Producer rules 37, 41; consumer rules 14, 28.
\item \textbf{Canonical register mnemonics} (Section~\ref{sec:threadctx}, Table~\ref{tab:regnames}): register names for x86\_64, x86, ARM64 and ARM32 are normative; aliases (\texttt{fp}, \texttt{lr}, \texttt{r13}--\texttt{r15}) are forbidden; consumers normalise \texttt{fp}$\to$\texttt{x29}, \texttt{lr}$\to$\texttt{x30}. Producer rule~42; consumer rule~29.
\item \textbf{Erratum:} 1.1.0 permitted trailing data after the AEAD tag but gave no means to locate the tag; the tag is now located via \field{CipherLen} (Sections~\ref{sec:enclayout}, \ref{sec:parsing}).
\end{itemize}

\noindent\textbf{1.1.0 --- 2026-10-23.} Minor revision; 1.0.0 files remain valid, consumers \MUST{} accept any minor of major~1 (Section~\ref{sec:versioncompat}).
\begin{itemize}[leftmargin=1.5em, itemsep=3pt]
\item \textbf{End-of-Capture \field{BlockCount}} (Section~\ref{sec:eoc}): the EoC payload now carries the exact capture-segment block count at \texttt{+0x28}; the header \field{BlockCount} is never patched after writing (Section~\ref{sec:basehdr}). A 40-byte legacy EoC payload remains accepted.
\item \textbf{Extension segments} (Section~\ref{sec:extsegments}): blocks appended after the EoC block are grouped into segments terminated by a new End-of-Extension block (\hex{0FFE}) with \field{SegmentHash}, \field{WrittenAt}, \field{BlockCount}, and \field{Producer}; the \field{PrevHash} chain continues across the EoC block. Evidence block types are forbidden in segments; producer-defined Structural payloads (e.g., Pointer Graph \hex{1003}) are permitted only there. Bytes after the last verified segment are trailing data.
\item \textbf{VAS Map} (\hex{1001}, Section~\ref{sec:vasmap}): payload defined (\field{Count}/\field{EntrySize} preamble, 24-byte entry head, \field{NameSource} at entry offset \texttt{+0x14}); one entry per enumerated range; the last map in file order supersedes.
\item \textbf{Page state NotResident} (\texttt{11}, Section~\ref{sec:threestate}): the former reserved value now denotes a mapped, never-touched page with zero content; Section~\ref{sec:threestate} renamed to ``Page State Map''; design principle~2 reads ``four-state''.
\item \textbf{New capture-time blocks}: Physical Memory Map (\hex{0059}, Section~\ref{sec:physmap}, not yet emitted by any known producer), Module Build-ID Manifest (\hex{005A}, Section~\ref{sec:buildid}), Region Omission Manifest (\hex{005B}, Section~\ref{sec:omission}); Connectivity Table (\hex{0054}, Section~\ref{sec:block:connectivity-table}) with \field{TableBitmap} bit~3 (Table~\ref{tab:sysctx-bitmap}).
\item \textbf{\field{HashAlgo}} (header offset \hex{3D}, Section~\ref{sec:hashchain}, Table~\ref{tab:hashalgos}): integrity hash selector (BLAKE3 default, SHA-256, SHA-512/256); producer rules 31--32 and consumer rule~22. Previously present only in the LaTeX edition.
\item \textbf{Thread Context} (\hex{0011}, Section~\ref{sec:threadctx}, Tables~\ref{tab:threadctx}/\ref{tab:threadreg}): per-thread register files contributed by Ricardo J. Rodr\'{\i}guez (PR~\#1), with \field{Arch} at \texttt{+0x13}, \field{Suspended}/\field{Partial} flags, thread states \hex{05}--\hex{07}, and register flags for thread pointer and link register.
\item Markdown and LaTeX editions synchronized: paper title, \field{HashAlgo}, Connectivity Table renumbered from \hex{0055} to \hex{0054}.
\end{itemize}
